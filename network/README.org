
** About
Neural network simulator developed by Felix Hoffmann for his PhD.
Original at https://github.com/synsrv/src_net.

Network simulation using Brian 2 and Pypet written to analyse the survivability of transient synapses of cortical neurons.

** Requirements
To run the network simulation a Python 3.12 environment with Brian 2 and Pypet is required.
The pinned dependencies are listed in ~environment.yml~; the upstream Brian2 release from PyPI is
used, no patched Brian2 version is needed anymore.

In addition, the following has to be installed on the system:
- Git
- a C++ compiler (~g++~), used by Brian2's ~cpp_standalone~ device
- LaTeX with the ~tgheros~, ~sansmath~ and ~siunitx~ packages, used for the figures

Below is an example installation routine for setting up a conda environment.
This assumes that you already have anaconda or miniconda installed.

#+BEGIN_SRC sh
#!/bin/sh

conda env create -f environment.yml
conda activate synlife

#+END_SRC

** Installation

It is highly recommended to limit the level of parallelization when building the standalone_cpp simulator.
In ~$HOME/.brian/user_preferences~ write, where ~4~ is the number of CPU cores your PC has:
#+BEGIN_SRC ini
[devices.cpp_standalone]
extra_make_args_unix = ["-j4"]
#+END_SRC

** Run a simulation
To verify your installation, within ~network/~ run

#+BEGIN_SRC sh
./run_test.sh tests/net_tests/test_standard_net/
#+END_SRC

This copies the code to ~tests/testing/<timestamp>_test_standard_net/~ (at the repository root),
runs the test simulation there and checks its results (~test.log~).

** Explore parameters

The parameters of a run are set in ~net/explored_params.py~ (defaults and documentation in
~net/standard_params.py~). Each entry of its ~input_dict~ is a list: lists of length n give n
simulations, matched column by column, and lists of length 1 are used for all of them. The
variable ~name~ labels the run. Then, within ~network/~:

#+BEGIN_SRC sh
./run.sh
#+END_SRC

runs all parameter sets in parallel (at most one per core) in
~running/<timestamp>_<name>/~, which is moved to ~completed/~ when finished. The git commit is
recorded with the results; uncommitted changes of tracked files are saved in
~uncommitted_changes.diff~ of the run folder. Options (~./run.sh -h~):

| ~-t~       | test run: no git record, results in ~tests/man/~                   |
| ~-b~       | run in the background (output in ~nohup.out~ of the run folder)     |
| ~-n N~     | at most N simulations in parallel (~4 GB each with N_e=1600)        |
| ~-P name~  | name of the run folder instead of ~name~                            |
| ~-D text~  | description, saved in the file ~description~ of the run folder      |

To run the post-processing of a finished run again (e.g. after changing the analysis code), use
~./src/post_process.sh~ from inside its run folder.

** Run on a Slurm cluster

From the repository root, ~sbatch submit.slurm~ runs ~run.sh~ on one whole node (all parameter
sets in parallel, all memory of the node, at most 12 h); options of ~run.sh~ can be added, e.g.
~sbatch submit.slurm -t~. The progress is written to ~synlife_<jobid>.log~. Add a partition or
~module load~ lines in ~submit.slurm~ if your cluster needs them.

The job uses the venv ~network/myenv~ if it exists, otherwise the conda environment ~synlife~
(of the conda installation in ~$CONDA_BASE~, default ~~/miniforge3~). Without conda, create the
venv on a login node (needs Python 3.12 and internet access):
~PYTHON=python3.12 network/setup_env.sh~. The packages are pinned in ~requirements.txt~ (same
versions as ~environment.yml~).

** Run tests

There are multiple sets of tests currently, they fall in three broad categories:
1. tests that can be run with ~pytest~: ~pytest tests/pytests~
2. unit tests of the analysis methods, run from within ~analysis/~: ~PYTHONPATH=. pytest test~
3. all other tests, which can be run using ~./run_test.sh~ as shown above
